## Architecture

Next.js 16 App Router application for INVITUS — a Ukrainian powerlifting equipment e-commerce brand. React 19, TypeScript, Tailwind CSS v4, pnpm.

### Tech Stack
- **Framework**: Next.js 16 (App Router, RSC by default)
- **UI**: React 19, Tailwind CSS v4, shadcn/ui (new-york style, add via `npx shadcn@latest add <component>`)
- **Animation**: Framer Motion (`motion` package) + `react-scroll-parallax`
- **State**: Zustand with persist middleware (cart store in `stores/cart.ts`, persisted to localStorage as `invitus-cart`)
- **Icons**: lucide-react
- **Carousel**: embla-carousel-react
- **Package Manager**: pnpm

### Component Organization
- `components/sections/` — Full-page landing sections (hero, product showcase, FAQ, testimonials, etc.). Each is a self-contained section with its own mock data.
- `components/ui/` — Reusable UI primitives (shadcn/ui base + custom: `product-card`, `cta-link`, `pointer`, `scroll-based-velocity`)
- `components/layout/` — Header (fixed nav with scroll effects, mobile menu, cart badge) and Footer

### Key Patterns
- **Dark mode is always on** — `<html>` has `className="dark"` hardcoded in root layout
- **Two font families**: Golos Text (body, `font-sans`) and Druk (headings, `font-heading`) loaded in `app/layout.tsx`
- **Path alias**: `@/*` maps to project root
- **Providers**: `app/providers.tsx` wraps the app with `ParallaxProvider` (client component boundary)
- **Type definitions**: `types/index.ts` defines `Product`, `CartItem`, `CartState`

### Styling

- Custom typography utilities: `text-h1`, `text-h2`, `text-h3`, `text-body-1`, `text-body-2`

### Products data (KeyCRM)
- Products, categories, prices, stock and photos come from the KeyCRM Open API (`https://openapi.keycrm.app/v1`). Requires `KEYCRM_API_TOKEN` in `.env.local` (server-only). Rate limit: 60 req/min.
- `lib/keycrm.ts` — low-level client (bearer auth, pagination). `lib/keycrm-schema.ts` — API response types. `lib/api.ts` — adapter mapping KeyCRM → domain types from `types/index.ts`; UI never imports KeyCRM schema.
- Product slugs are generated by slugifying the KeyCRM product name. Category id → site slug mapping is hardcoded in `lib/api.ts` (`CATEGORY_SLUG_BY_ID`).
- Sizes/variants come from KeyCRM offers (`/offers?filter[product_id]=…`), fetched only on the product page.
- **A size has two halves and they are not interchangeable** (`ProductSize` in `types/index.ts`): `value` is KeyCRM's own ("S") and is what the cart stores, the order posts and `lib/orders.ts` matches an offer by; `label` is what the customer reads ("65-80 см"). Belts are stocked as letters but sold by waist range, so the join is the **offer SKU** — Strapi variants carry the centimetre name plus the KeyCRM SKU, and `lib/product-extras.ts` turns that into `sizeLabelsBySku`. Matching on the letter instead would break the four belts that have XS/XL/2XL/4XL; matching on list position would mislabel them silently. A size Strapi says nothing about falls back to KeyCRM's value.
- KeyCRM stores the variant axis as a **free-text property name per offer**, and the catalogue uses two: `Розмір` for belts/knee sleeves/straps, `Довжина` for wrist wraps. Both are read in `lib/variant-property.ts`, imported by `lib/api.ts` and `lib/orders.ts` so the selector and the pricing can never disagree, and the order echoes back the property the offer actually uses. A product whose offers carry neither cannot be ordered at all — the adapter logs a warning naming it (Guts Lifting Belt files S/M/L under `Колір`, which is a data error to fix in KeyCRM, not a third axis to accept).
- **Presentation content is hybrid**: KeyCRM has no marketing content — 3D models, hero/bg images, howToMeasure, careInstructions and `featured` come from **Strapi** via `lib/product-extras.ts`, matched by the `keycrmId` integer field on the Strapi product (rename-proof) or, failing that, by slugified **name** — `slugify(keycrm.name) === slugify(strapi.name)`. Note it is *not* Strapi's own `slug` field, which uses a different convention ("belt-poseidon" vs "poseidon-lifting-belt") and matches nothing. Resilient: 3 attempts × 12s, last-known-good index kept in memory, 60s back-off — a down Strapi degrades to fallbacks and never blocks rendering. `content/product-extras.ts` (keyed by KeyCRM product id) is the offline fallback layer. Filter tags are not wired up (catalog shows only "УСІ").
- **Merchandising lives in Strapi, and every lever fails open** (see issue #25). Three of them: `Product.order` (integer, numbered **per category** in steps of 10) drives catalog order; the `Homepage` single type's `showcase` / `shopCta` relation lists pick the two homepage rows independently; `Product.relatedProducts` drives product-page cross-sell. Strapi 5 preserves manual relation order, so all three are drag-to-reorder. **The `Homepage` single type is readable only with the API token** (products are public), so `STRAPI_API_TOKEN` must be set in `.env.local` and in Vercel env vars (server-only) or the homepage sections sit on the `featured` fallback forever, warning on every render. The rules that make them safe: a product with **no `order` sorts last**, not nowhere (a product created in KeyCRM minutes ago has no Strapi entry yet, and a Strapi outage must degrade the catalog to KeyCRM creation order rather than to an empty page); each row falls back **curated → `featured` → catalog order** and is always topped up to four, because a four-column grid with three cards reads as a bug; a curated entry that resolves to no live KeyCRM product is dropped with a `console.warn` naming it. `featured` is now only that emergency layer, not the everyday tool.
- `scripts/backfill-strapi-placement.mts` (`pnpm backfill:placement`, dry-run by default, `--apply` to write) is the one-off that gave every Strapi product its `keycrmId` and a clean per-category `order`. Idempotent, so re-run it after adding a product in both systems. Note a plain `PUT /api/products/:documentId` on Strapi 5.34 writes through to the **published** version, not just the draft — verified against production; there is no publish step to do afterwards.
- **Strapi freshness is webhook-driven, not timer-driven**: the extras fetch is cached for 24h and invalidated on demand by `POST /api/revalidate`, which Strapi calls on publish (Settings → Webhooks, header `Authorization: Bearer <REVALIDATE_SECRET>`). Requires `REVALIDATE_SECRET` in `.env.local` and in Vercel env vars (server-only). Pulling content only when it changes is what keeps a Strapi outage at an arbitrary moment from being captured into a cached render — see the note at the top of `lib/product-extras.ts`.

### Checkout
- Page route: `app/checkout/page.tsx`. Components in `components/checkout/`. Reusable form primitives in `components/ui/` (`labeled-field`, `icon-input`, `searchable-select`, `radio-card`).
- Form validation via React Hook Form + Zod. Schema lives in `lib/checkout-schema.ts`.
- Delivery uses Nova Poshta. Browser hits a server proxy at `app/api/nova-poshta/route.ts` → forwards to `api.novaposhta.ua` (NP blocks direct browser fetches). Client code in `lib/nova-poshta.ts` + hooks in `hooks/use-nova-poshta.ts`. Requires `NOVA_POSHTA_API_KEY` in `.env.local` (server-only, never reaches the client bundle).
- **Email is required, and required for cash on delivery too.** The rule lives in `lib/checkout-schema.ts` and is restated in `app/api/orders/route.ts`, because the browser is no more the authority on it than it is on prices — the two schemas are deliberately separate and their bounds (`max(320)`) are kept in step by hand. The reason it is not conditional on the payment method: on an online payment the address is where Monobank's receipt goes (`customerEmails` on the invoice — omit it and a paid order produces no written record at all), and on any order it is the only way KeyCRM can reach the customer about something a phone call cannot carry. The site still sends **no mail of its own** — there is no mail dependency in the project — so for cash on delivery the address is collected, not yet written to. `lib/checkout-schema.test.ts` locks the rule, including that a missing address says «Вкажи email» while a malformed one says «Невірний email».
- **Orders are placed server-side** — the browser POSTs *what* was ordered (KeyCRM product id, size, quantity) to `app/api/orders/route.ts`; it never sends prices. `lib/orders.ts` re-prices every line from KeyCRM (`min_price`, the figure the catalog shows), totals it in `lib/order-totals.ts`, creates the order via `POST /order`, then asks Monobank for an invoice for *its own* total. Touches Strapi for one thing only — promo codes, and only through the cache described below, which is what keeps the CMS off the critical path; nothing else in the payment path may depend on it.
- **The site charges nothing for delivery** — the customer pays Nova Poshta on collection, so the order total is the goods and nothing else (issue #31, owner's decision). The checkout's delivery line reads «Тарифи оператора» and is the whole story; `shipping_price` on the KeyCRM order is always `0`; the Monobank invoice no longer carries an `EXTRA_CHARGE` line to make up the difference; and the product JSON-LD carries no `shippingDetails`, because a rate of `0` would advertise free shipping, which is a different promise. The flat 120 ₴ `SHIPPING_COST` (and `lib/shipping.ts`) was **deleted rather than zeroed** — a constant at `0` with a "TODO: real rate API" comment reads as an unfinished feature instead of a decision.
- **Promo codes are the one place the payment path is allowed to read the CMS** (issue #48). Codes live in Strapi's `PromoCode` type; `lib/promo-codes.ts` reads them exactly the way `lib/product-extras.ts` reads extras — retries, in-memory `lastGood`, 60s back-off, single-flight, a 24h window busted on publish by `/api/revalidate` (its own tag, `strapi-promo-codes`, invalidated on the same webhook so switching off a leaked code takes effect on the next checkout rather than a day later). The exception to «платіжний шлях не залежить від CMS» is bought by that machinery: a short Strapi outage is invisible, and only a process that has *never* read the list refuses a code — with an explanation, never by silently charging full price. Its per-attempt budget is deliberately **not** the extras loader's 12s: this runs with a customer waiting, and the free tier's cold start was measured at 14.6s, so 12s loses that race three times in a row. It is `[20s, 8s]` — win the cold start outright, then a short retry against an instance the first attempt already woke.
- **What a code is worth is decided in one pure function**, `evaluatePromoCode` in `lib/promo.ts`, called by both the checkout's `/api/promo` and by `priceOrder()` — so the figure on screen and the figure on the invoice cannot be two implementations that merely agree today. Base is the goods only (#31 left nothing else to discount); the discount is `Math.round`ed to whole hryvnia (a fractional one renders as «3 809,5» and puts copecks in the Monobank amount) and clamped to the subtotal, so `fixed: 200` on a 150 ₴ cart is a 150 ₴ discount and never a refund. A **date-only `activeTo` lasts to the end of that day** — Strapi's Date field has no time, and taking `2026-08-09` literally kills the code before anyone shopped on the 9th. The kill switch is checked before the dates so a withdrawn code says it was withdrawn, and a missing `isActive` reads as off.
- **The browser sends the code string and nothing else.** The cart's promo state (`stores/promo.ts`, `invitus-promo`) persists the *code* and never the discount — a discount restored from localStorage is one nobody agreed to pay. It is re-earned from the server on checkout mount and on every cart change, and re-checked again inside `priceOrder()`; a code that stopped qualifying in between fails the order with `PromoRejectedError`, which the endpoint flags as `promoRejected` so the checkout drops the code and re-renders rather than leaving it sitting applied next to a message saying it isn't. No usage counters, deliberately — a global limit needs atomic storage this project doesn't have, and KeyCRM's `/order` filters cannot query `promocode`. Brute-forcing is not defended against either (WAF rate limits are Pro; the project is Hobby) — the answer to a leaked code is unticking `isActive`.
- **KeyCRM takes `promocode` and `discount_amount` at the order root** — verified on write, not just on read, before being relied on (test orders #1024–#1026 on product 44): both come back unchanged and KeyCRM subtracts the discount itself, so `grand_total` equals the payment amount. Line prices stay **catalogue** prices, so a manager sees both the promotion and what the goods normally cost. On the Monobank side the promo is a **basket-level `discounts` entry**, never a negative basket line, which would print on the fiscal receipt as goods.
- Two KeyCRM payload quirks, both found the hard way: `shipping_price` belongs at the **root** of the order (inside `shipping` it is silently dropped and `grand_total` comes back goods-only, disagreeing with the amount charged), and the Nova Poshta `city_ref`/`warehouse_ref` go **flat inside `shipping`**, not nested in an `address_payload` object. With the refs present KeyCRM resolves the address against Nova Poshta itself, filling in the region and the official branch name.
- Orders arrive with `stock_status: null` — sending the SKU does not by itself reserve the variant. Reservation still has to be sorted out.
- Requires `KEYCRM_SOURCE_ID`, `KEYCRM_PAYMENT_METHOD_ID_ONLINE` and `KEYCRM_PAYMENT_METHOD_ID_COD` (numeric KeyCRM ids, server-only). They have no defaults — a wrong guess would file real orders under the wrong source, so the code throws when they are unset.
- **Payment confirmation is the webhook, not the redirect** — `app/api/monobank/webhook/route.ts` verifies the `X-Sign` header (ECDSA-SHA256 over the raw body, key from `/api/merchant/pubkey`) and marks the KeyCRM payment paid. `/payment-result` is only what the customer sees; closing the tab after paying still lands a paid order.
- **Online payments** — `paymentMethod === "online"` redirects through Monobank acquiring. Client → `app/api/orders` → Monobank → `app/payment-result` (status check + cart clear on success). Server-side client in `lib/monobank.ts`. Requires `MONOBANK_TOKEN` in `.env.local` (server-only). Status endpoint at `app/api/monobank/status`. Test tokens available at https://api.monobank.ua/.

### Blog
- **Articles are written as Markdown in `content/articles/` and stored as Strapi `blocks`.** Nobody writes Blocks JSON by hand — it is verbose and one bad nesting level is a record the API rejects *after* the article was written — so `scripts/markdown-to-blocks.mts` is the bridge and `scripts/publish-article.mts` (`pnpm publish:article`, dry-run by default, `--apply` to write) drives it. The converter sits in `scripts/` and not `lib/` **on purpose**: its parser is a devDependency, and putting it where a page could import it would turn a build failure on Vercel into the way you find out. Anything a page needs — the block types, `readingTimeMinutes` — lives in `lib/article-body.ts`, which has no imports at all.
- **The converter refuses rather than guesses, always with a line number.** An `#` (the page's only h1 is the `title` field), a `---`, a code fence, a table, raw HTML, an image sharing a line with text, an image with no uploaded media. Bulk-generated articles are not read closely enough for a silent mangling to be caught before it ships, so there is no quiet mode; each message names what to write instead.
- **Two Strapi shapes were found by writing into a real instance rather than by reading types, and both are silent traps.** An image block carries the *whole* media entry — `{ id, url }` alone comes back with eleven validation errors — so `REQUIRED_MEDIA_FIELDS` is checked before upload. And a **nested list is a sibling of its parent item, not a child of it**: Strapi answers "Inline node must be Text or Link" to the Markdown-shaped nesting, so the converter hoists sub-lists.
- **A quote is the red callout panel and the blog has no other quote style**; an image caption lives on the **media entry**, not in the body, so it travels with the file. Reading time is computed from the body (words ÷ 200, never 0) rather than stored — a field the author fills starts lying the first time the text is edited. On the real article it lands on the 5 minutes the design prints.
- **Publishing order is deliberate**: front matter is validated, then the body is converted against stub media (which checks the whole document *and* collects its images), then files are checked to exist — and only then is anything uploaded. A bad article costs nothing and leaves no orphaned media. Uploads are normalised to 1600px WebP q80 for Strapi Cloud's storage quota, named `<slug>-<stem>.webp` so a re-run reuses them, and a changed caption **re-writes** the existing entry rather than reporting "reused" and doing nothing. Articles are created as **drafts** — publishing stays a human action in the admin.
- Image binaries are **gitignored**: the repo is the source of truth for article text, Strapi for the binaries — the same line already drawn for 3D models and product photos.

### Performance budget
- **A viewport unit is never multiplied.** The belt scrub's runway used to be `700vh`, and on mobile that was a bug rather than a style: the browser chrome collapses and expands as you scroll, so the viewport height moves, and seven times a ~100px toolbar is ~800px of height change in a section sitting above most of the page. WebKit has no scroll anchoring to absorb it — measured at 375x752 → 375x852, the content below jumped 800px while the finger was still moving, and in an in-app browser (which resizes its web view outright) it is worse. Both viewport-sized boxes on the homepage now take their height from `useStableScreenHeight` (`hooks/use-stable-screen-height.ts`): a pixel value re-measured **only when the viewport width changes**, since a height-only change is the toolbar and nothing else. Two details are load-bearing and tested in `lib/stable-viewport.ts`. The value is read from a throwaway element sized in **`svh`**, not from `window.innerHeight` — `svh` is what the server-rendered fallback already painted, so the hydration shift is zero by construction rather than merely small, which matters because the hero is the LCP element and the CLS gate is `0`. And `ScrollTrigger.config({ ignoreMobileResize: true })` stops GSAP recomputing every trigger mid-scroll, which is what made the cards look like they were re-snapping. The product page's `100svh` hero is deliberately left alone: it lives in a `hidden lg:block` desktop layout, where the chrome does not move.
- **Videos live on Vercel Blob, posters live in the repo.** `lib/blob.ts` names the one Blob origin (the homepage `preconnect`s to it, so a second origin would need a second hint). The hero is the pattern: `public/assets/hero-poster.webp` is the LCP element, same-origin, 19 KB, with the greyscale and the 30% opacity over `#1a1a1a` **baked into the pixels** so it and the video's first frame are the same picture — the fade-in is invisible. The video itself is not requested until after the `load` event, and not at all when `shouldLoadDecorativeVideo` in `lib/video-conditions.ts` says no (`save-data`, a slow `effectiveType`, or `prefers-reduced-motion`). Re-encoding it hard was free because it renders greyscaled at 30% under a 60% black overlay; regenerate the poster from the video's first frame whenever the clip is recut, or the two will drift apart. **The video fades in inside an opaque `#1a1a1a` wrapper, not as a bare 30% layer** — fading the bare video over the poster leaves the poster visible through its remaining 70%, which is a permanent still of frame one ghosted under the motion and a hero brighter than the design (measured: 16× the pixel deviation from poster-alone).
- **Every video below the fold goes through one primitive, and that is the point.** `<LazyVideo>` (`components/ui/lazy-video.tsx`) over `useVideoGate` (`hooks/use-video-gate.ts`): the element renders from the first paint so the box never changes size, but the `src` is attached only once the section is within a viewport and a half, and playback pauses the moment it leaves the screen. The same three signals as the hero — `save-data`, a slow `effectiveType`, `prefers-reduced-motion` — are read from `lib/video-conditions.ts`, and when they say no the source is never attached at all; `onActiveChange` is how a section learns that, so it can drop controls that would otherwise sit over an empty box. The gate opens only after hydration **and after the `load` event**, which is what keeps the server from rendering a `src` and what stops a section close enough to the fold to sit inside its own load margin — the belt scrub is about two screens down — from being fetched during the page load this whole thing exists to protect. One escape hatch, `essential: true`: the scrub's 700vh of card animation is driven off the video's own duration, so skipping it leaves seven screens of a single card. Such a video is still deferred, only never skipped — `save-data` is an ask for less, not an ask for a broken section. It is not for keeping a decorative video alive. **Reach for `useVideoGate` directly only when a section needs the gate but not the playback** — a carousel choosing which of its videos plays, or a scrub whose `currentTime` comes from scroll. The three videos #34 found each downloading on page load were three separate mistakes made because this rule lived nowhere; adding a fourth video without it would be the fourth.
- **3D models are compressed before they reach Strapi, and the weight is all textures.** Measured on the catalogue: **97% of a belt's bytes are PNG textures**, several of them 4096², against ~1 MB of geometry — so Draco and meshopt, the obvious first reach, are a rounding error until the textures are dealt with. The agreed recipe is **resize to 2048 → WebP quality 80 → meshopt**, in that order, which took the heaviest belt from 40.6 MB to 2.23 MB (18×) and its download from ~6.5 s to 1.5 s. Quality was checked at the scale the texture is actually sampled at on screen, not at 1:1 on the source: PSNR 38.6 dB on base colour and 38.7 dB on the normal map (>40 dB is the usual "indistinguishable" line, and the normal map is the slot that fails first). Neither half needs anything added to the app — three reads `EXT_texture_webp` natively, and the meshopt decoder is already attached in `components/models/dynamic-model.tsx`. **KTX2/Basis was rejected**, not overlooked: it would need `setKTX2Loader` wiring plus a `toktx` binary in the pipeline, and its real advantage is GPU memory rather than transfer — WebP decompresses fully into VRAM, which only starts to matter if a page ever shows several models at once.
- **three.js reaches the browser through exactly one `import()`, in `components/models/model-viewer.tsx`.** Imported statically it lands in the product route's *entry* chunk, and since Next prefetches that route the moment a product card scrolls into view, the homepage downloaded 283 KB (≈1 MB unpacked) to render no 3D at all. Behind the dynamic import it is a chunk of its own. **Do not import `model-loader` directly** — a static import anywhere in a routed component graph silently undoes this, and nothing fails to build when it happens. Deferring alone would only trade a slow homepage for a slow product transition, so the chunk is *warmed*: `warmModelViewer()` on pointer-enter / touch-start of a `ProductCard`, and `useWarmModelViewerWhenIdle()` once per product-listing page as the fallback for visitors who never hover. That fallback is the delicate part, and it is why `lib/idle-after-load.ts` exists as a separate tested module: scheduled before the `load` event it pulls the chunk straight back into the measurement window and cancels its own benefit while looking correct in review. Under `save-data` the idle warm is skipped entirely and only intent warms — deferring is not refusing. Route prefetching stays on; it was never the problem, it was simply fetching the wrong thing.
- `perf/budget.json` holds the homepage thresholds (LCP, transfer weight before `load`, Speed Index, CLS as gates; TBT as a soft target). `pnpm perf:lighthouse` builds, serves and measures against it in a **clean Chrome profile with no extensions** — the original slow-homepage report was taken with five extensions live and credited the site with ~2 MB of someone else's JavaScript. Lighthouse 13 dropped built-in budgets, so `scripts/perf/evaluate-budget.mjs` enforces them. Baseline numbers and what the harness does *not* measure (analytics never loads on localhost) are in `docs/perf/lighthouse.md`.
