## Architecture

Next.js 16 App Router application for INVITUS — a Ukrainian powerlifting equipment e-commerce brand. React 19, TypeScript, Tailwind CSS v4, pnpm.

### Tech Stack
- **Framework**: Next.js 16 (App Router, RSC by default)
- **UI**: React 19, Tailwind CSS v4, shadcn/ui (new-york style, add via `npx shadcn@latest add <component>`)
- **Animation**: Framer Motion (`motion` package) + `react-scroll-parallax`
- **State**: Zustand with persist middleware (cart store in `stores/cart.ts`, persisted to localStorage as `invitus-cart`)
- **Icons**: lucide-react
- **Carousel**: embla-carousel-react
- **Package Manager**: pnpm

### Component Organization
- `components/sections/` — Full-page landing sections (hero, product showcase, FAQ, testimonials, etc.). Each is a self-contained section with its own mock data.
- `components/ui/` — Reusable UI primitives (shadcn/ui base + custom: `product-card`, `cta-link`, `pointer`, `scroll-based-velocity`)
- `components/layout/` — Header (fixed nav with scroll effects, mobile menu, cart badge) and Footer

### Key Patterns
- **Dark mode is always on** — `<html>` has `className="dark"` hardcoded in root layout
- **Two font families**: Golos Text (body, `font-sans`) and Druk (headings, `font-heading`) loaded in `app/layout.tsx`
- **Path alias**: `@/*` maps to project root
- **Providers**: `app/providers.tsx` wraps the app with `ParallaxProvider` (client component boundary)
- **Type definitions**: `types/index.ts` defines `Product`, `CartItem`, `CartState`

### Styling
- Tailwind CSS v4 with CSS variables for theming in `app/globals.css`
- Custom typography utilities: `text-h1`, `text-h2`, `text-h3`, `text-body-1`, `text-body-2`
- Custom layout utility: `container-main` (centered container, max 88rem, `clamp(1.5rem, 5vw, 2rem)` padding — min 24px on mobile). Override via `[--container-px:value]`.
- Custom theme variable: `--radius-section` for section border radius — 32px on mobile, 48px on md+ (768px+)
- Primary brand color: `#E74223` (coral)
- Animation utilities from `tw-animate-css`
- Class merging via `cn()` from `lib/utils.ts` (clsx + tailwind-merge)

### Content & Locale
- All UI text is in Ukrainian
- Prices formatted in UAH (₴) using Ukrainian locale
- SEO metadata in Ukrainian

### Products data (KeyCRM)
- Products, categories, prices, stock and photos come from the KeyCRM Open API (`https://openapi.keycrm.app/v1`). Requires `KEYCRM_API_TOKEN` in `.env.local` (server-only). Rate limit: 60 req/min.
- `lib/keycrm.ts` — low-level client (bearer auth, pagination). `lib/keycrm-schema.ts` — API response types. `lib/api.ts` — adapter mapping KeyCRM → domain types from `types/index.ts`; UI never imports KeyCRM schema.
- Product slugs are generated by slugifying the KeyCRM product name. Category id → site slug mapping is hardcoded in `lib/api.ts` (`CATEGORY_SLUG_BY_ID`).
- Sizes/variants come from KeyCRM offers (`/offers?filter[product_id]=…`), fetched only on the product page.
- **A size has two halves and they are not interchangeable** (`ProductSize` in `types/index.ts`): `value` is KeyCRM's own ("S") and is what the cart stores, the order posts and `lib/orders.ts` matches an offer by; `label` is what the customer reads ("65-80 см"). Belts are stocked as letters but sold by waist range, so the join is the **offer SKU** — Strapi variants carry the centimetre name plus the KeyCRM SKU, and `lib/product-extras.ts` turns that into `sizeLabelsBySku`. Matching on the letter instead would break the four belts that have XS/XL/2XL/4XL; matching on list position would mislabel them silently. A size Strapi says nothing about falls back to KeyCRM's value.
- KeyCRM stores the variant axis as a **free-text property name per offer**, and the catalogue uses two: `Розмір` for belts/knee sleeves/straps, `Довжина` for wrist wraps. Both are read in `lib/variant-property.ts`, imported by `lib/api.ts` and `lib/orders.ts` so the selector and the pricing can never disagree, and the order echoes back the property the offer actually uses. A product whose offers carry neither cannot be ordered at all — the adapter logs a warning naming it (Guts Lifting Belt files S/M/L under `Колір`, which is a data error to fix in KeyCRM, not a third axis to accept).
- **Presentation content is hybrid**: KeyCRM has no marketing content — 3D models, hero/bg images, howToMeasure, careInstructions and `featured` come from **Strapi** via `lib/product-extras.ts`, matched by the `keycrmId` integer field on the Strapi product (rename-proof) or, failing that, by slugified **name** — `slugify(keycrm.name) === slugify(strapi.name)`. Note it is *not* Strapi's own `slug` field, which uses a different convention ("belt-poseidon" vs "poseidon-lifting-belt") and matches nothing. Resilient: 3 attempts × 12s, last-known-good index kept in memory, 60s back-off — a down Strapi degrades to fallbacks and never blocks rendering. `content/product-extras.ts` (keyed by KeyCRM product id) is the offline fallback layer. Filter tags are not wired up (catalog shows only "УСІ").
- **Merchandising lives in Strapi, and every lever fails open** (see issue #25). Three of them: `Product.order` (integer, numbered **per category** in steps of 10) drives catalog order; the `Homepage` single type's `showcase` / `shopCta` relation lists pick the two homepage rows independently; `Product.relatedProducts` drives product-page cross-sell. Strapi 5 preserves manual relation order, so all three are drag-to-reorder. **The `Homepage` single type is readable only with the API token** (products are public), so `STRAPI_API_TOKEN` must be set in `.env.local` and in Vercel env vars (server-only) or the homepage sections sit on the `featured` fallback forever, warning on every render. The rules that make them safe: a product with **no `order` sorts last**, not nowhere (a product created in KeyCRM minutes ago has no Strapi entry yet, and a Strapi outage must degrade the catalog to KeyCRM creation order rather than to an empty page); each row falls back **curated → `featured` → catalog order** and is always topped up to four, because a four-column grid with three cards reads as a bug; a curated entry that resolves to no live KeyCRM product is dropped with a `console.warn` naming it. `featured` is now only that emergency layer, not the everyday tool.
- `scripts/backfill-strapi-placement.mts` (`pnpm backfill:placement`, dry-run by default, `--apply` to write) is the one-off that gave every Strapi product its `keycrmId` and a clean per-category `order`. Idempotent, so re-run it after adding a product in both systems. Note a plain `PUT /api/products/:documentId` on Strapi 5.34 writes through to the **published** version, not just the draft — verified against production; there is no publish step to do afterwards.
- **Strapi freshness is webhook-driven, not timer-driven**: the extras fetch is cached for 24h and invalidated on demand by `POST /api/revalidate`, which Strapi calls on publish (Settings → Webhooks, header `Authorization: Bearer <REVALIDATE_SECRET>`). Requires `REVALIDATE_SECRET` in `.env.local` and in Vercel env vars (server-only). Pulling content only when it changes is what keeps a Strapi outage at an arbitrary moment from being captured into a cached render — see the note at the top of `lib/product-extras.ts`.

### Checkout
- Page route: `app/checkout/page.tsx`. Components in `components/checkout/`. Reusable form primitives in `components/ui/` (`labeled-field`, `icon-input`, `searchable-select`, `radio-card`).
- Form validation via React Hook Form + Zod. Schema lives in `lib/checkout-schema.ts`.
- Delivery uses Nova Poshta. Browser hits a server proxy at `app/api/nova-poshta/route.ts` → forwards to `api.novaposhta.ua` (NP blocks direct browser fetches). Client code in `lib/nova-poshta.ts` + hooks in `hooks/use-nova-poshta.ts`. Requires `NOVA_POSHTA_API_KEY` in `.env.local` (server-only, never reaches the client bundle).
- **Orders are placed server-side** — the browser POSTs *what* was ordered (KeyCRM product id, size, quantity) to `app/api/orders/route.ts`; it never sends prices. `lib/orders.ts` re-prices every line from KeyCRM (`min_price`, the figure the catalog shows), adds `SHIPPING_COST` from `lib/shipping.ts`, creates the order via `POST /order`, then asks Monobank for an invoice for *its own* total. Deliberately does not touch Strapi: a payment path must not depend on the CMS.
- Two KeyCRM payload quirks, both found the hard way: `shipping_price` belongs at the **root** of the order (inside `shipping` it is silently dropped and `grand_total` comes back goods-only, disagreeing with the amount charged), and the Nova Poshta `city_ref`/`warehouse_ref` go **flat inside `shipping`**, not nested in an `address_payload` object. With the refs present KeyCRM resolves the address against Nova Poshta itself, filling in the region and the official branch name.
- Orders arrive with `stock_status: null` — sending the SKU does not by itself reserve the variant. Reservation still has to be sorted out.
- Requires `KEYCRM_SOURCE_ID`, `KEYCRM_PAYMENT_METHOD_ID_ONLINE` and `KEYCRM_PAYMENT_METHOD_ID_COD` (numeric KeyCRM ids, server-only). They have no defaults — a wrong guess would file real orders under the wrong source, so the code throws when they are unset.
- **Payment confirmation is the webhook, not the redirect** — `app/api/monobank/webhook/route.ts` verifies the `X-Sign` header (ECDSA-SHA256 over the raw body, key from `/api/merchant/pubkey`) and marks the KeyCRM payment paid. `/payment-result` is only what the customer sees; closing the tab after paying still lands a paid order.
- **Online payments** — `paymentMethod === "online"` redirects through Monobank acquiring. Client → `app/api/orders` → Monobank → `app/payment-result` (status check + cart clear on success). Server-side client in `lib/monobank.ts`. Requires `MONOBANK_TOKEN` in `.env.local` (server-only). Status endpoint at `app/api/monobank/status`. Test tokens available at https://api.monobank.ua/.
